# ADR-013 — Canonical IDs Use Provider-Independent UUIDv7

**Status: ACCEPTED / LOCKED FOR V1**  
**Date: 2026-09-14**

## Context
Every durable Cinema and Series entity requires a stable internal identity independent of IMDb, TMDB, Wikidata, TheTVDB or any other provider.

The IDs must work for distributed ingestion/workers, remain portable between PostgreSQL hosts, avoid centralized integer-sequence coupling, index reasonably and never encode mutable business facts such as title/year/language.

RFC 9562 defines UUIDv7 as a time-ordered UUID. PostgreSQL 18 includes native `uuidv7()`, while current Supabase projects may run earlier PostgreSQL versions; PostgreSQL's `uuid` type can store standards-compliant UUIDs regardless of where they are generated.

Sources reviewed:
- https://www.rfc-editor.org/rfc/rfc9562.html
- https://www.postgresql.org/docs/18/functions-uuid.html
- https://www.postgresql.org/docs/18/datatype-uuid.html

## Decision
Durable CAS canonical/domain entity IDs use **RFC 9562 UUID Version 7**, stored in PostgreSQL's native `uuid` type.

IDs are generated in the trusted application/worker domain layer using a standards-compliant UUIDv7 library until every supported database environment offers a native function we deliberately choose to depend on.

We do **not** require PostgreSQL 18 merely for ID generation.

## Applies to
At minimum:
- Work
- Version
- Series/Season/Episode structural entities where separately keyed
- Person
- Organization
- ReleaseEvent
- Asset
- SourceSnapshot
- Claim
- CanonicalDecision
- MusicalWork / MusicRecording
- review/action records where durable cross-system identity matters
- domain events/outbox records

Very local join rows may use composite keys or other internal strategies where a separate global ID adds no value; physical schema decides that explicitly.

## Namespace / public representation
The stored canonical ID is the UUID, not a provider-style prefix string.

Human/API context determines entity type through endpoint/schema.

Where a globally self-describing textual reference is useful, represent it at the boundary as:
- `cas:work:<uuid>`
- `cas:person:<uuid>`
- `cas:org:<uuid>`

This is a representation/URI convention, not a second primary key.

## Why UUIDv7
- globally unique without external provider;
- time-ordered, improving locality compared with fully random v4 IDs;
- standardized by RFC 9562;
- works across TypeScript/Python/PostgreSQL;
- does not reveal title/provider semantics;
- supports offline/batch creation before central insert;
- future PostgreSQL native generation is compatible with the stored type.

## Creation timestamp rule
UUIDv7 contains time information, but **entity `created_at` remains a separate authoritative database column**.

Never use UUID timestamp extraction as the only audit timestamp. IDs may be generated before persistence, imported through replay, or generated by multiple trusted processes.

## External IDs
All provider identifiers live in `ExternalIdentifier` mappings.

Examples:
- IMDb `tt...`
- TMDB numeric ID
- Wikidata QID
- TheTVDB ID
- EIDR
- ISAN
- MusicBrainz MBID

They may be added, removed, redirected or disputed without changing the CAS ID.

## Merge behavior
When entities merge:
- one CAS ID becomes the surviving canonical identity;
- losing CAS IDs are **never reused**;
- redirects/tombstone mappings preserve resolution from old CAS IDs;
- merge history is auditable/reversible according to Identity Resolution spec.

A split creates new UUIDv7 IDs as required and preserves lineage.

## URL slugs
Friendly title/person slugs are optional mutable routing helpers and are never identity.

Example:
`/movie/019.../rrr`

Changing the title/slug must not change the canonical ID.

## Security note
UUIDs are identifiers, not authorization secrets. Knowledge of an ID must never grant access to privileged resources.

## Rejected alternatives
### Auto-increment bigint as universal ID
Rejected as the cross-system canonical identity: tightly centralizes generation and is less suitable for distributed batch/worker creation.

### Provider IDs
Rejected absolutely as primary identity.

### Title/year hashes
Rejected because mutable/ambiguous metadata would make identity unstable.

### Random UUIDv4 as default
Valid technically, but UUIDv7 offers useful temporal/index locality without encoding business semantics.

### Custom opaque base62/ULID format as storage PK
Rejected to avoid inventing a private ID standard when UUIDv7 is now standardized and directly supported by PostgreSQL's UUID type.

## Validation / implementation rules
- trusted factories generate v7 UUIDs;
- tests verify version nibble/standards compliance;
- imports cannot choose provider IDs as CAS IDs;
- database constraints may validate UUID version where practical, but domain factories are the primary generation contract;
- Postgres native `uuidv7()` may later be used after an ADR amendment if all environments support it.
